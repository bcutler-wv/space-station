# 0004: Owner authentication

Status: Implemented in M0.4, pending Compose and browser CI review.

Use Fastify's cookie, session, CSRF, and rate-limit plugins, a PostgreSQL session-store adapter, SimpleWebAuthn, otplib 13, and the node-rs Argon2id binding. The session adapter hashes each opaque session ID before database storage; it strips bearer fields from JSON, rejects revoked rows, expires sessions after 30 idle minutes or seven days, and blocks a stale save after logout. Fastify handles cookie signing, serialization, session rotation, and CSRF token verification. The adapter handles only persistence policy. Secure, HttpOnly, SameSite Strict `__Host-` cookies remain fixed even in local tests.

Owner creation and its chosen credential, confirmed second factor, and ten hashed recovery codes commit in one PostgreSQL transaction. A local CLI writes a 0600 bootstrap token to a bind-mounted private path and stores only its SHA-256 hash for 15 minutes. Database advisory locking and a fixed owner primary key reject races and replay. Passkey ceremonies require user verification, exact configured origin and RP ID, a five-minute single-use challenge, and atomic counter updates. Password hashes use Argon2id with 64 MiB and three passes. TOTP verification records the accepted time step and rejects replay. TOTP seeds are encrypted with the master key. Recovery codes are random, hashed, shown once, and consumed atomically.

`APP_ORIGIN` is an exact HTTPS origin. Disposable local development uses a private self-signed localhost certificate generated by `scripts/init-env.mjs`; runtime browser tests exercise direct HTTPS with Secure cookies. A reverse proxy deployment must configure its exact trusted source IP so Fastify accepts its forwarded HTTPS scheme. State-changing requests require an exact Origin header and the Fastify CSRF token. The API protects all appearance and wallpaper reads and writes. Health and readiness remain public with minimal responses. The local shell still contains sample data after sign-in; account connection and privacy choices belong to M1.

Password recovery uses the password and a recovery code, then requires enrollment and confirmation of a new TOTP seed. Passkey recovery consumes a code before requiring registration and user verification of a replacement passkey; all existing sessions and recovery codes are revoked when the new credential is confirmed. The recovery code is the possession factor for passkey-only accounts. No email recovery exists.
