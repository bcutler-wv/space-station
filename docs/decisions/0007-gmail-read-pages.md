# 0007: Gmail read pages and rejected-token recovery

Date: 2026-10-20

M1 Gmail ingestion uses explicit read pages from the official `@googleapis/gmail` 22.0.2 SDK. The durable runner owns page tokens, the frozen cutoff, and cursor commits. A read call may replay once after a 401 only after `GoogleCredentialService` compares the rejected token value and generation and obtains a different published token or a freshly refreshed token. A claimed refresh lease can advance the generation without publishing a token, so generation alone never proves freshness. The SDK receives only the access token and cannot independently refresh it. Send and modification calls do not use this path.

The installed Gaxios 8.3.1 source checks `Content-Length` but does not guarantee a byte limit for a streamed body before JSON parsing. Gmail read requests therefore use a fixed Gmail host and a fetch response stream limit, with redirects rejected. Both top-level SDK retry and nested `retryConfig` are disabled. Raw message bytes are decoded only after bounded JSON and base64url validation. The supported decoded raw limit matches the parser's 12 MiB input limit. An oversized successful response is classified as too large; an oversized provider error body stays transient. Retry-After is a scheduling hint without an inline wait or shortening the provider's stated delay; numeric values beyond safe millisecond precision clamp to the maximum safe integer. Provider `SENT` label metadata supplies trusted Sent provenance.
