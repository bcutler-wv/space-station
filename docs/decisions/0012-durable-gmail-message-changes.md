# Durable Gmail message changes

## Decision

Archive, mark read, mark unread and add/remove existing user labels are explicit owner actions on one selected Gmail message. The browser supplies an item ID, exact account/optional Orbit, current applied sequence and provider revision, a desired action and an idempotency UUID. The server resolves the selected item's provider ID and freezes it with explicit add/remove label IDs, scope and revision in `mail_change_operations`. It writes a content-free audit intent in the same transaction. The send-specific `outbound_operations` constraints remain intact.

Before a write, the server gets a credential through the existing service, checks any requested label with `users.labels.get` for exact ID and `type: user`, and checks the message with `users.messages.get` for exact ID and absence of `DRAFT`. It then rechecks current item/scope/revision, label resolution and credential generation, and commits a one-attempt claim before `users.messages.modify`. Gmail may omit an empty `labelIds` array. A present malformed array, mismatched message ID, timeout, redirect or failed HTTP response after claim is an unknown write outcome. The official SDK transport has fixed host, 64 KiB response cap, ten-second deadline and zero retries.

An idempotency replay returns the existing operation. An exact owner/item/account/Orbit/idempotency-key status lookup recovers a lost POST response. Pending, in-flight and unknown operations block a different action on the item across item sequences. A settled attempted success blocks a different action until the item's applied sequence advances and its local sync update is later than operation completion. This is a conservative action gate, not proof that the provider read happened after the write. A failed operation before claim permits a new explicit request. If provider preflight already observes the desired state, the operation succeeds with `observed` confirmation and zero attempts; it does not block a later action at the same sequence. Status and account/Orbit-scoped signed-cursor discovery are read-only. A stale pending operation can be failed explicitly; a stale in-flight operation is treated as unknown. Explicit reconciliation performs only a bounded message read under the current credential and may record that the desired state was observed. Direct provider response and later observation are different confirmation values; neither proves another Gmail client did not later change labels.

## Consequences

The route never mutates local item, label, revision, sequence or privacy evidence. Existing Gmail history/polling sync supplies the local label refresh, and the UI must report labels as pending refresh until a causally fresh item read is known. M2 index/AI consumers must deny derived processing for an item with an action at its current frozen sequence, including a zero-write observed no-op, until an authoritative provider item read initiated after settlement verifies labels. A history event might not arrive for a no-op, so M2 must be able to request such a read. A local update timestamp alone cannot prove provider-read order. Action concurrency and derived eligibility are separate rules. No derived consumer exists in M1. No GET/open auto-read behavior, AI action path, provider drafts, thread-wide mutation, delete/trash, label creation or classification labels are included.

The API choice follows the [Gmail `messages.modify` method](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/modify), [label resource type](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.labels), and [label behavior guide](https://developers.google.com/workspace/gmail/api/guides/labels), checked 2026-10-21. It uses the already pinned Apache-2.0 `@googleapis/gmail` 22.0.2 SDK; no dependency was added.
