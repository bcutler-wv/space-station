# Stopped search administration job lock

This bounded source slice adds a single owner-local `.cache/search-db/.job-operation.lock` shared by both supported DB inspectors and the explicit credential command. The lock order is job then credential. Retained verification runs after both locks are acquired; the launcher holds the job lock through service validation and confirmed one-shot completion. Both inspectors therefore serialize with each other and with credential work. Direct Docker-owner commands remain outside this local convention.

The lock has a create-exclusive 0600 inode and a synced, nonsecret operation identity. Before remote inspector dispatch, the launcher syncs a second fixed record identifying the role and dispatch. A positive Compose completion releases the owned inode. A timeout, crash, transport failure or otherwise unconfirmed completion leaves the lock for explicit owner diagnosis. No timer or PID check automatically removes it. Definite pre-dispatch failures release only their own lock inode. A replaced pathname is never intentionally unlinked by finalization.

The initial credential create, retained verify and pending-create abort protocol is otherwise unchanged. In particular, an uncertain owner database mutation remains blocked by the pending bundle's `.owner-operation-inflight` marker even after the outer job lock releases. The lock does not rotate credentials, start a scheduler or enable either search gate. Actual two-UID Ubuntu delivery validation remains a prerequisite for integration of this source slice.

Version 0.52.0 integrates this slice after the actual dual-identity inspector gate passed at `2858eca`, run `39848694782`. Astra independently reviewed the source, process contention/uncertainty fixture, fixed Compose boundary and original credential lifecycle on a fresh PostgreSQL 15 cluster. Local application checks passed. The added process fixture and actual PG16/Compose regressions must now pass in Ubuntu with the shared lock before runtime acceptance.
