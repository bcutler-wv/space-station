# Fixed attestor delivery services

Version 0.64.0 is source accepted after independent Astra review, fake configuration denials, real local Compose rendering and the full 154-test local check. Ubuntu rendering and actual container delivery remain separate gates.

`compose.search-attestor.yaml` is selected explicitly with the ordinary Compose file. It adds three opt-in, one-shot services and requires invocation-specific variables only when selected. The existing verifier and transition inspectors and ordinary Compose commands retain their prior configuration. No service starts as part of normal application startup.

`search-attestor-prepare` runs as the configured nonroot owner pair on only `search_admin_db`. It receives the exact verifier password read-only and the owner-owned invocation tree read-only at `/run/search-attestor`; a nested manifest-directory bind is writable so the fixed preparation command can publish its mode 0600 manifest beneath the original mode 0700 parent. `search-attestor-transfer` runs as `0:0` with no network and only CHOWN and DAC_OVERRIDE added after dropping all capabilities. Its four read-only bind inputs are the exact verifier password file, invocation file, manifest file, and public-only staged tree. Its one writable persistent mount is the external invocation volume. `search-engine-attestor` runs as `1000:1000` on exactly `search_admin_db` and `search_internal`, with only that volume read-only, the existing admin TLS volume read-only, and the bootstrap state volume read-only. Its private `/tmp` is for OpenSSL checks over captured public bytes.

All three have read-only root filesystems, no published ports or dependencies, no new privileges, no automatic restart, and fixed commands. Prepare and transfer each have 64 PIDs, 256 MiB memory, 0.5 CPU, and an 8 MiB private `/tmp` tmpfs. The combined attestor has 128 PIDs, 512 MiB memory, 1 CPU, and a 64 MiB private `/tmp` tmpfs. Bind mounts use `create_host_path: false`; invocation volume mounts use `nocopy: true`. The invocation volume is declared `external: true` with a UUID-derived explicit name, so Compose cannot create an absent one. The owner launcher remains responsible for positive volume creation and actual container, mount, network, UID, capability and completion evidence.

The pure validator checks the normalized, service-scoped Compose JSON against trusted project, owner pair, invocation, paths and volume name. It accepts only the three fixed services and their exact network, mount, command, capability and resource shapes. The scaffold fixture tests substitutions and added authority. The dedicated-image Ubuntu job renders the overlay for fake owner pairs `1000:1000` and `1001:1001` and checks the normalized result without launching those services. Configuration rendering does not prove actual mount permissions or delivery; the later C4 launcher gate must do that.

The render proof was also run locally without a Docker daemon using the checksum-verified official Docker Compose v5.6.1 standalone CLI. Both fake owner pairs and the unselected base configuration passed. Its normalized output includes safe defaults (`entrypoint: null`, `build.dockerfile: "Dockerfile"`, and empty network `ipam`), which the validator accepts while rejecting changed values. The proof uses a disposable fixture root and fake environment file, leaving the repository's private environment file untouched. The Ubuntu CI render is still required for this task.
