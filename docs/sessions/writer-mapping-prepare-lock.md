# Writer-mapping proposal preparation lock

Version 0.97.0 adds a named, uncalled `writer-mapping-prepare` mode to the existing exclusive `.cache/search-db/.job-operation.lock`. The mode records transfer dispatch/confirmation, read preparation dispatch/confirmation, checked owned cleanup, and a pending attempt/prepared confirmation in exact order. Each durable append is protected by the original opened lock and root identity, file and directory sync, and an attempt latch before I/O. A checked local preflight with no external attempt can release. Its mapping-only `retainPreflightFailure()` latches a `preflight failed` record before append and forbids another dispatch or release when future owner-local cleanup is uncertain; the later owner must call it because the lock cannot inspect those local resources. An attempted uncertain operation fails closed. Normal same-call completion permits release only after the final prepared record. A release failure after removing the lock can leave the path absent, so later pending-file evidence must deny replay even if the lock is lost.

Real-filesystem tests exercise record order, concurrency, successful no-attempt cleanup, an actual failed local directory removal with its child still present, preflight and every later phase append/fsync fault, terminal retry refusal, same-byte lock/root replacement and release failures before/after removal. This mode is not yet called by an owner and does not create or validate a pending proposal; no Docker, database mutation, mapping send, signer, fingerprint or readiness authority follows. The preceding 0.96.1 exact-commit Ubuntu run `41945990934` at `13339e6289cc90623c92952442d31bc294b4729c` passed all 25 jobs with Astra acceptance; the new mode's own Ubuntu regression is pending.
