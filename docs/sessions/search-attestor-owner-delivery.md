# Fixed owner attestor delivery source

Version 0.65.0 is source accepted after independent Astra rereview of PostgreSQL container identity and actual mount-option checks. Both focused owner fixtures and the full local check passed, including 154 tests, lint, typecheck, build, color and license gates. The lockfile and dependency versions are unchanged. Actual Ubuntu delivery remains required in C4e2; no live search gate is enabled.

C4e1 connects the reviewed prepare, offline transfer and combined attestor commands under one owner-local search-admin job lock. The launcher takes no path, phase, command, recovery or UID arguments. Its process UID/GID must match `APP_UID`/`APP_GID`, and the lock creates the sole invocation UUID. The source is not accepted as working container delivery until C4e2's disposable Ubuntu PostgreSQL/OpenSearch TLS gate passes for both owner pairs.

Under the lock, the launcher reuses retained credential verification and the existing Docker installation identity adapter. It captures the original verifier password and metadata bytes, mode, owner and inode without printing them. The adapter exposes its already validated PostgreSQL admin-network ID and endpoint for capture and later comparison; the launcher also captures the PostgreSQL container ID. Every owner recheck repeats credential verification and compares the full installation, endpoint and container identities. A new invocation may accept an ordinary PostgreSQL container recreation, but one invocation cannot silently switch containers. The prepared manifest's numeric database OID must match the retained canonical decimal OID text. The in-container commands keep both SQL gates false and independently compare their DB snapshots.

The launcher creates one private invocation root with a 0400 UUID file and a 0700 manifest output directory. It validates service-scoped normalized Compose config, existing private networks and retained admin/state volumes, and locally built image IDs before a send. A durable lock mark precedes each of three detached `docker compose run --no-deps --pull never` sends, and the transfer mark precedes volume creation. The invocation volume must be positively absent before exactly one creation request; the owner compares its name, driver, scope, creation time, labels and options before each use. No ambiguous response is retried or adopted.

The owner re-renders and compares the exact scoped Compose configuration before each send. Each captured full container ID is inspected against its fixed image, command, inherited reviewed entrypoint and environment, UID, capabilities, resources, mounts, network IDs and terminal state. Both the effective `Mounts` inventory and `HostConfig.Mounts` options must match the finite configuration: invocation mounts require actual `NoCopy: true`, bind mounts must not create missing source paths, and extra mount options or alternate propagation/subpaths fail. Absent or explicit false bind creation and absent or explicit false writable-mount read-only flags are equivalent safe Engine defaults. Exact stdout acknowledgments, empty stderr and exit zero are required before confirmation. Prepare's manifest is captured and validated before owner-only public staging. Transfer runs offline and copies only that finite input list into UID/GID 1000. The final job runs fixed 1000:1000 with the intended two networks and read-only input/admin/state volumes. The owner rechecks original source, staged output, credentials, endpoint and invocation-volume identities before final dispatch and after completion.

Success cleanup compares the completed container identities, refuses any extra stopped or running invocation-volume reference, removes only those captured containers and the same volume, then removes captured public and invocation inodes with canonical ancestor checks before lock release. A local failure after a confirmed remote phase conservatively retains the lock and artifacts in this slice. A pre-dispatch owned cleanup failure also records a conservative prepare attempt without sending Docker and retains the lock. A phase with an uncertain remote outcome never triggers cleanup. Volume deletion is ordinary cleanup, not secure erasure.

The fixed CLI prints only a generic failure. Docker subprocess output is capped, each call has a timeout, the core checks a 240-second whole-invocation budget, and the wrapper has a hard 240-second process deadline. A process timeout can leave a remote CLI or job outstanding; it is never treated as completion and leaves lock/artifacts for private inspection. Cooperative owner/Docker-admin control is assumed. Sequential DB and engine observations are not an atomic cross-system snapshot; no publication or serving gate is enabled.

The C4e2 disposable Ubuntu gate uses a fresh checkout and Compose project for each configured owner/prepare identity pair. It boots real PostgreSQL 16 and OpenSearch 3.9 TLS, exercises the unmodified fixed CLI with the E0b complete marker and again with grantless legacy state, and probes actual container mounts, capabilities, network isolation, copied UID-1000 inventory, retained credentials, E0b modes and disabled SQL gates. Failure cases wrap only the test-side Docker command seam around real sends to simulate lost responses, drift, replacements, references and cleanup refusal. The fixture explicitly tears down its own resources after asserting lock and artifact retention; that teardown is not an owner recovery path. The gate must pass in Ubuntu before actual delivery is accepted. No secret-bearing output is uploaded.

The fixed Docker adapter now checks the single short-syntax `/tmp` declaration through exact `HostConfig.Tmpfs` options and requires inspect `.Mounts` to contain only the declared bind and volume mounts. Current [Compose source](https://github.com/docker/compose/blob/main/pkg/compose/create.go#L357-L363) sends service-level `tmpfs` separately from volumes; [Moby v28.5.2](https://github.com/moby/moby/blob/v28.5.2/container/container_unix.go#L370-L410) likewise separates `HostConfig.Tmpfs` from the mount points returned by container inspect. Scripted evidence now rejects missing, extra or changed tmpfs options, a fabricated `/tmp` inspect entry, and injected bind or duplicate mounts. This is a source-based compatibility correction; actual Ubuntu behavior is still required for acceptance.

The 0.66.3 Ubuntu delivery run 40582094393 passed all 19 migrations, credentials, search initialization, OpenSearch startup and security bootstrap, then failed at profile introduction with exit 1; its redacted output does not prove the cause. A local tar proof showed that the fixture's mode-077 umask strips source read/traverse bits during default extraction. The fixture now uses `tar -xpf` for the initial checked-out source copy and probes the built image's fixed profile-introduction code path as UID 1000 with no network. [GNU tar](https://www.gnu.org/software/tar/manual/html_node/Setting-Access-Permissions.html) documents the permission behavior; [Docker](https://docs.docker.com/reference/dockerfile/#copy---chown---chmod) documents local-context `COPY` permission preservation and default root ownership. The static cause remains an inference until the next Ubuntu run supplies actual image and delivery evidence.
