# Security

Station holds a person's entire working life: every email, chat, and calendar event across every organization. Treat it accordingly.

## Threat model

| Threat | Main controls |
|---|---|
| Malicious email content (XSS, tracking, exploits in parsing) | Sanitized rendering, sandboxed iframe, image proxy, isolated MIME parsing |
| Prompt injection through any message | No AI action tools, direction rules, schema-only output (see AI.md) |
| Someone reaching the web app | Not exposed publicly by default, strong auth, rate limits |
| Theft of the database or backups | Provider credentials encrypted at rest; restricted file permissions and encrypted backups for message contents and metadata |
| Supply chain (npm) | Short, pinned dependency list, lockfile, audit and license checks in CI |
| Data sent to AI providers | Exclusion rules, per-Orbit AI policy, local model option, no AI required |

## Rendering email

- Sanitize HTML with DOMPurify, with a mail-specific config. SnappyMail's sanitizer rules (AGPL-3.0, compatible) are a good reference for email-specific edge cases.
- Render inside a sandboxed iframe (no scripts, no same-origin, no forms) with a strict content security policy.
- All remote images go through go-camo. Remote images are blocked by default with a "Load images" button, per message and per sender.
- The image API accepts only an account, item, optional Orbit and opaque stored reference. It rechecks live item visibility, policy version, image metadata and consent before fetching. A CSRF-protected message choice or an account-scoped preference for the message's single claimed normalized From address permits remote images. The address is sender-supplied and is not an authenticated identity. CID images may load by default only from related attachments on the same item and account. An authenticated POST fetch is required even for CID images; reading body or consent metadata never fetches an image.
- Remote sources must use HTTP or HTTPS on the standard port without URL credentials. The first proxy release follows no redirects, so images whose source redirects are unavailable. The proxy blocks private and metadata destinations at dial time. The app converts supported raster formats to bounded PNG and returns private no-store bytes; SVG and other active/vector formats are unavailable.
- Image database statements have transaction-local three-second statement and 750-millisecond lock deadlines. Each short transaction closes before private blob access, proxy fetch or Sharp processing. Four simultaneous image jobs reserve their worst-case 6 MiB of input/output against a 32 MiB per-message minute budget; failures after input starts consume that full reservation, while successful small images have a 32 KiB minimum charge. Sharp's three-second processing timeout starts when libvips opens the input and does not cover queue time or the whole HTTP route.
- Proxying hides the client IP, but fetching a unique tracking URL can still reveal that a message was opened. Do not describe the proxy as preventing tracking.
- Links show their real destination on hover and open with `rel="noopener noreferrer"`.
- Re-sanitize at render time even though content was sanitized at ingest.
- The browser reads ref kinds from the authenticated, account/Orbit-scoped image-consent response. It receives only opaque IDs and `remote`/`cid` kinds, never stored source URLs or signed proxy URLs. The browser requires the body and consent ref sets to match exactly before rendering HTML. Its parent fetches at most 64 PNGs, each at most 2 MiB and together at most 32 MiB, and embeds them as data URLs in the opaque-origin frame. Base64 expands that displayed byte ceiling to roughly 43 MiB of source text before DOM copies; consent changes and unmount abort requests and clear the data. Blob URLs from the parent cannot load in that opaque-origin frame.
- The `station:logout` lifecycle immediately clears private body, consent and image state and aborts pending body, image, font and setting requests. Item and Orbit changes invalidate prior request completions before the new scoped body appears.
- A current explicit per-message choice takes precedence over a claimed-sender preference. If no choice exists, or the message source digest has changed, the sender preference applies. Thus "Block images in this message" works while a sender preference remains enabled; the UI reports the effective choice.

## Parsing

- MIME parsing runs in a separate process/container with cgroup memory and CPU limits, input-size caps, and a wall-clock timeout. Node worker-thread limits alone do not cap external buffers. A malformed message fails alone.
- The parser service is limited to 512 MiB, one CPU core, 64 processes/threads, and two concurrent children. Raising its former half-core quota gives DOMPurify and jsdom more CPU during concurrent near-cap messages; memory, concurrency, input, and elapsed-time limits remain enforced. The worker does not receive raw HTML.
- M1.3a accepts at most 12 MiB raw MIME, 8 MiB total decoded attachments, 4 MiB combined text/HTML, 16 MiB JSON output, 64 KiB aggregate headers, 128 parts, 16 MIME levels, three nested RFC822 levels, 100 recipients, and 64 attachments. M1.3b uses an eight-second child deadline, an 8.5-second whole-request limit, a ten-second worker-client timeout, and two concurrent requests per parser service. The raw cap supports roughly 8 MiB of base64 attachments; larger messages are unsupported. Limit failures are classified and must become visible unsupported records during later sync; cursors must not silently skip them.
- M1.3b sanitizes HTML inside that killable child before it crosses to the worker. It accepts at most 512 KiB of decoded HTML, 1 MiB of sanitized HTML output, 64 image references, and 2,048 characters per image URL. It rejects oversize HTML as `limit_exceeded`. The result carries a policy version, safe HTML, and opaque image references with separately bounded remote or CID sources. No image source is left in a browser-loadable attribute; the parser performs no network fetch. A CID source is untrusted until a later account/item-local attachment lookup. These limits are a support boundary and later sync must show an unsupported record for a rejected message.
- Ingest sanitation does not make stored HTML permanently safe. The reader must use the shared policy to re-sanitize it in a sandboxed iframe. The policy strips all incoming `data-station-image-ref` attributes, including generated ones; the reader must reconstruct placeholders only for IDs proven against the separately validated, bounded stored image metadata. It must not trust an HTML attribute as authority to fetch. The stored remote URL is untrusted metadata, and later go-camo signing must independently check DNS, redirects, and SSRF boundaries. Remote images stay blocked until the user asks to load them. M1.3b provides no persistence or reading path.
- Attachment text extraction runs in the Tika container, never in the app process.
- Attachments are served with `Content-Disposition: attachment` and a safe content type unless they are images shown inline through the proxy.

## Authentication

- Passkeys, or password plus TOTP. Optional OIDC. Passwords use a one-way Argon2id hash with per-password salt and versioned parameters, never reversible encryption. TOTP seeds are encrypted; recovery codes are hashed and one-time use.
- First-run owner creation is a one-time transaction guarded by a bootstrap token delivered through a local setup command, never a log. Disable the bootstrap endpoint after ownership exists. Require a second factor for credential reset; provide one-time recovery codes at enrollment. No email-only recovery path.
- Sessions in HTTP-only, Secure, SameSite=Strict cookies.
- Store only hashed session tokens server-side; rotate after login or privilege changes and revoke on logout. Expire idle and absolute sessions. CSRF protection on every state-changing request, including same-site deployments.
- Rate limits on login and on the API.

The current API limit is 120 requests per minute per client IP, and owner login has a separate five-attempt-per-minute limit. Exhaustion returns HTTP 429 with `Retry-After`; clients should not treat that response as a CSRF or credential failure.

M0.4 requires an exact configured HTTPS `APP_ORIGIN` for state-changing requests, in addition to per-session CSRF tokens. Local development uses a private localhost TLS certificate; reverse proxy deployments name one trusted proxy source IP. Password-plus-recovery-code access is restricted to a new confirmed TOTP seed; it cannot read or change private settings before confirmation. A forgotten password can be replaced with both a current TOTP code and an unused recovery code. If both are lost, there is no account recovery path. Recovery of a passkey-only account consumes a code and requires user verification on a new passkey. Replacing any credential increments the owner auth generation, invalidates pending old logins and recovery attempts, revokes prior sessions, and rotates recovery codes.

The sync progress REST endpoint and SSE stream are passive reads: loading or reconnecting them does not extend the 30-minute idle session. Ordinary authenticated requests continue to refresh activity. A separate stream watcher checks the stored hashed session, expiry, revocation and owner generation every two seconds, including during replay. A session-check query has a 1.5-second application deadline and closes the stream on timeout. SSE authorization and replay read transactions also set local PostgreSQL statement and lock timeouts of 1.25 and 1 second, so a blocked query releases its database client without waiting for the lock holder. A network partition can still delay PostgreSQL's detection of a lost connection. Logout and credential reset close established streams across processes. Events contain only a fixed name, monotone ID and account UUID, and clients refetch private REST state after a reset. The server caps streams, replay and output buffering and closes slow clients.

## Secrets

- OAuth tokens, client secrets, IMAP passwords, and AI keys are encrypted with a master key (AES-256-GCM, envelope encryption) from `STATION_MASTER_KEY` in the environment. Password hashes are separate and never decryptable.
- Losing the master key means re-connecting every account. The docs and the wizard say this plainly.
- Secrets are never logged. Logs redact tokens, addresses in query strings, and message bodies.
- Mail bodies, attachments, metadata, and indexes are sensitive even though application-level encryption covers credentials only. Limit volume permissions and encrypt backups/storage where the host supports it; test restore without printing private content.
- The optional OpenSearch runtime candidate uses a private CA and separate node, administrator, query, and indexer mTLS identities. Only a networkless init sees the CA private key; the engine receives its node identity, and no current app or worker receives a search identity or network attachment. Query and indexer methods use fixed-index, bounded SDK operations, while retained security roles and mappings must pass explicit verification before a profile is accepted. Its container security gate remains pending Ubuntu validation and no live index or serving authority exists yet.
- The private blob store accepts at most 16 MiB per file, uses generated keys only, rejects symlinks at its configured root and on reads, and publishes by exclusive hard link after syncing a private temporary file. The configured root's ancestors must be administrator-owned and trusted; the Compose mount satisfies this. It does not expose paths to the browser. This bound does not raise the parser's lower MIME and decoded-attachment limits. The volume is writable only by the app group; the parser has no mount. Containers sharing this group are trusted with blob contents.
- Draft attachment uploads use exact-origin, owner-session and CSRF checks before consuming raw bytes. At most four upload handlers run concurrently. Each retains an 8 MiB upload allocation and can briefly hold another 8 MiB plus one byte for published-file verification, for roughly 64 MiB across four handlers plus incoming stream chunks. A 30-second timer aborts the upload signal and closes the request; filesystem cancellation is cooperative and the handler keeps its concurrency slot until it settles. A committed draft intent precedes immutable publication; writer and bounded collector serialize on its row lock. A stale revision after publication leaves a collectible intent. A draft row lock serializes reservation and the 8 MiB total/64 file quota. The five-minute worker collector reclaims pending or detached draft blobs after a one-minute grace period, checking current draft and pending outbound references first. No sync page owns these files. Stored file names are untrusted metadata; download uses a safe Unicode attachment name, octet-stream, no sniff, no preview and no cache.
- Gmail send requires an owner session, exact configured Origin and CSRF token. Two concurrent handlers bound attachment plus MIME preparation and provider settlement. A durable operation reserves a private MIME key and freezes at most 12 MiB of exact bytes before the one provider call. The raw Gmail payload retains Bcc for provider routing. A committed provider claim cannot be retried automatically; crash recovery marks it unknown and reconciliation only reads Sent. A missing Sent result never authorizes a resend. Audit entries contain operation IDs and outcome names, not message content or tokens. Failed blobs are collected after grace; confirmed blobs after 30 days; unresolved unknown blobs remain for manual resolution.
- Mail persistence first records a durable blob intent tied to the account and sync page. Publication holds the intent row lock. A later page transaction checks the same row and file before creating its reference. Cleanup skips live page leases, takes the intent lock, and checks database references before removing published and temporary files. A tombstone removes read eligibility before physical cleanup. The worker schedules bounded collector runs every five minutes.
- Private mail-reader GETs require a full current owner session and count as user activity. List cursors are signed and bound to account, Orbit, label and subject filters; a request after deletion cannot resolve the item or attachment. Reader database stages use read-only transactions with local three-second statement and 750-millisecond lock deadlines; blob reads begin after the transaction closes. The server caps list pages at 30 records and 512 KiB, one body response at 32 MiB including JSON escaping, and attachment downloads at 8 MiB. Body text retains the parser's 4 MiB bound and stored HTML has a 1 MiB bound. Missing, corrupt, oversized or policy-incompatible HTML returns an unavailable state without exposing the blob path. Downloads use opaque item and attachment IDs, Unicode-safe filenames, `Content-Disposition: attachment`, `application/octet-stream`, and `nosniff`.

## Privacy precedence and retention

- Before sync starts, the wizard asks for global and first-Orbit indexing/AI exclusions. For each item, combine the account Orbit, routed Orbits, and global rules; the most restrictive applicable effect wins. `no_index` excludes lexical and vector indexes. `no_ai` excludes all model requests, embedding providers, AI-derived summaries, briefings, extraction, proposals, and citations. A local embedding service still follows the configured no-AI rule.
- M1.1 stores explicit global and first-Orbit defaults plus bounded exact account-email, sender-email, and provider-label-name exclusions. Empty Orbit membership or a missing Orbit policy denies indexing and AI. The versioned setup marker must gate later account connection and sync. There is no synced or derived content to purge in M1.1; later processing must enforce the policy and invalidation rules below.
- M1.3 mail persistence retains all parsed sender identities and resolved provider label names. Policy checks consider every sender identity and Orbit membership; unresolved label names deny indexing and AI. Source records remain available for ordinary mail use. No indexing or AI consumer is enabled by this task.
- A Gmail label action leaves the last synchronized labels untouched. Its settled transaction increments the item's action epoch; unresolved actions independently deny derived use. The worker captures the epoch and durable authorization generation before a raw provider item read and persists those values with credential-generation provenance only in a supported normalized page. A read started before settlement or grant change cannot clear the barrier merely by committing later. No-op actions may emit no history event, so a bounded, paced ready-stage refresh re-reads stale supported items through the normal fenced page path. Historical rows start with null authorization observation and require bounded revalidation. Reconnects, changed scopes and definitive denials advance durable authorization generation; ordinary unchanged-grant token refresh only advances the short-lived credential fence and leaves completed item eligibility intact. Revocation, deletions, unsupported parses and unknown outcomes independently deny derived use. Local applied sequence or update time alone cannot prove provider-read order. The reusable derived eligibility query combines this evidence and the current global, every-Orbit, every-sender and resolved-label policy in one bounded read-only repeatable-read snapshot. Source-policy evaluation also requires a complete versioned setup marker; partial marker data cannot grant. A returned grant is a snapshot, not a publication fence: future index/AI producers and serving paths must revalidate current eligibility and scope when they publish or return derived data. No derived consumer or purge job exists yet.
- Enforce policy when scheduling work and again when serving search/CAPCOM or constructing provider requests. Attachments and OCR inherit the parent item's policy. Summaries and answers inherit the most restrictive policy of their sources.
- The M2 operator parser accepts only bounded user text and emits a typed Boolean AST. Its grammar is generated at build time; user input is never evaluated as a grammar or interpolated into a search-engine filter. A parsed AST is not an authorization grant. Later lowering and serving must apply exact owner scope and current derived eligibility without flattening mixed text/filter OR.
- When policy tightens or routing changes, block access immediately and queue deletion/invalidation for search documents, chunks and embeddings, extraction output, attachment extracted text if prohibited, summaries, briefings, citations, and cached answers. Rebuild only under the new policy. Record the purge job and surface failures until repaired.

## OAuth and network requests

- Build redirect URIs from the configured public origin, allowlist exact origins and provider authorization/token endpoints, and bind each OAuth callback to a short-lived server-side state record and the initiating authenticated session. Use PKCE where supported; reject replay and mismatched state before token exchange.
- A cross-site OAuth return may omit the Strict session cookie. Validate state and retain the callback result briefly on the server, then redirect to a clean same-origin continuation page. Its authenticated confirmation request must verify the original session before exchanging the code or linking credentials. Expire pending results, consume state once, and never log callback codes or put them in the continuation URL.
- Server-side URL fetches (autoconfig, attachments, proxying, AI-compatible endpoints) need scheme/port allowlists, DNS and redirect validation, private/link-local/metadata IP blocking where the target is untrusted, response size/time limits, and no forwarding of internal credentials. Document any explicitly trusted LAN model endpoint exception.

## Outbound actions

- Sending, archiving, deleting, and posting only happen from an explicit user action in the UI.
- Every outbound action is written to `audit_log`.

## Network

- Station runs fine with no public exposure (LAN or tailnet).
- Only the app container is published. The default binding is loopback. The other containers have no published ports; the Compose bridge permits outbound requests needed by later connectors.

## Dependencies

- Prefer fewer, well-maintained packages.
- Lockfile committed. CI runs `pnpm audit` and a license check that fails on GPL-2.0-only or unknown licenses.
- Copied third-party code keeps its header and is listed in THIRD_PARTY.md.

## Reporting

A `SECURITY.md` at the repo root (to add before the first public release) should give a private reporting address.
